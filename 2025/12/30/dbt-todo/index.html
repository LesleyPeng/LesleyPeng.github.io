    • tr_opnd_ process.cpp 中的接口 CODEX 待整理

    • 更加具体的问题是：为什么翻译jmp *0x200aba(%rip)，调用了convert_ir1_opnd_to_ir2_opnd()和convert_ir2_opnd_to_ir2_src_opnd()这两个接口，最后得到的加载目标地址static_translate.cpp:612-616，发射的ir2如下：
      li s6, 0
      ori s6, s6, 284
      ld t3, 0(s6)

    • convert_ir1_opnd_to_ir2_opnd() 只把“RIP 相对内存操作数”变成“可用的有效地址寄存器”，而 convert_ir2_opnd_to_ir2_src_opnd() 才会真正把这个地址对应的内存值加载出来。你看到的三条指令正好是“地址构造 + 内存读取”的组合。

      结合 jmp *0x200aba(%rip) 的路径：

      • 地址构造发生在 convert_ir1_opnd_to_ir2_opnd()
        • 这条操作数是 IR1_OPND_MEM_RIP，会走 convert_ir1_mem_opnd_to_ir2_reg_opnd() → load_ir1_mem_opnd_to_ir2_reg()。
        • 在 tr_opnd_process.cpp 里，load_ir1_mem_opnd_to_ir2_reg() 对 RIP-relative 在静态翻译模式下走 GENERATE_REL_ITEM 分支，发射：
          • PseudoLAImm + ADDI + ORI 这种“占位/重定位”序列（用 counter 做标记）。
        • 最终你看到的
          • li s6, 0
          • ori s6, s6, 284
            实际上就是这套 relocation 占位的输出形式（PseudoLAImm 被打印成 li，ORI 带着 counter）。
      • 内存加载发生在 convert_ir2_opnd_to_ir2_src_opnd()
        • 进入该函数后发现 ir1_opnd->is_mem()，非向量大小，于是分配临时寄存器并调用 tr_generate_ir2_load_from_memory()。
        • 对 64-bit mem 会发射 LD，所以有：
          • ld t3, 0(s6)
            这一步才把 “jmp table 里的目标地址值” 读到 t3。

      所以这三条指令的分工是：

      1. li s6, 0 + ori s6, s6, 284 → 生成 RIP-relative 目标表项的地址（静态重定位占位）。
      2. ld t3, 0(s6) → 从该地址读出真实跳转目标。

    • BIN_INFO<Elf64_Ehdr, Elf64_Phdr, Elf64_Shdr, Elf64_Sym>这个结构中存储的加载信息mmap_addr是在什么阶段存储进去的？

    mmap_addr 是在 “mmap 成功返回之后” 记录进 E64_BIN_INFO 的。具体是在 BIN_INFO::record_after_mmap 里赋值给 _mmap_addr，调用发生在处理 mmap 的路径中。

    关键位置：（==sc是syscall系统调用缩写，sci表示syscall implementation系统调用实际的实现函数==）

    • sc_mmap.cpp (line 301)：mmap 返回后调用 E64_BIN_INFO::record_after_mmap(fd, file_type, retval, len)，其中 retval 就是 mmap 返回的地址（即 mmap_addr）。
    • bininfo.h (line 791)：record_after_mmap 内部写入 _mmap_addr 和 _mmap_len。
    • 另外在加载器路径也会调用记录逻辑：loader.h (line 85)、loader.h (line 182)、loader.h (line 281)。

    简言之：mmap 系统调用成功返回后（loader/dlopen 或 syscall 入口），立即记录 mmap_addr。

    llvm中关于移除bb基本块节点的接口区别

    • 能否将处理静态翻译部分call的目标是否存在那一部分for (auto &pseudocall: pseudocall_to_fix)中的接口removeFromParent()换成eraseFromParent()或者eraseFromBundle()，以节省中for (auto &callin: callin_reloc_to_generate)

    不建议直接把 removeFromParent() 换成 eraseFromParent() / eraseFromBundle() 来“省掉 if (!instr->getParent()) continue;”，因为这会引入 悬空指针 风险。

    关键点：

    • removeFromParent() 只是把指令从 BB 链表里摘掉，但 不释放对象，所以后面拿 instr 指针做 getParent() 判断是安全的。
    • eraseFromParent() 会 删除对象。你后面的 pushx86addr_reloc_to_generate / callin_reloc_to_generate 循环里还会解引用 instr，这时指针已经失效，属于 UAF（崩溃/未定义行为）。
    • eraseFromBundle() 同理，也会删除对象，只是针对 bundle 内指令。

    所以：不能用 erase 来替代，只靠移除不能保证后续安全。
    如果你想去掉 if (!instr->getParent()) continue; 的分支，有两种更稳的做法：

    1. 移除时同步更新容器
      • 在 removeFromParent() 后，把该 RelocInfoPair 的 first 置为 nullptr，或直接从容器里删掉。
      • 后续就用 if (!instr) continue; 或遍历时跳过空指针。
    2. 推迟删除
    • 先统一处理完所有 pushx86addr/callin 重定位，再在最后集中 eraseFromParent() / removeFromParent()。
    • 这样就不需要中途 getParent() 判断。

    如果你希望，我可以帮你改成“容器里置空 + 统一跳过空指针”的方式（最小侵入），或者把删除延后到最后。

    • DBT本身需要支持多线程：code cache同步，全局env同步，快慢表同步；涉及到dbt优化的全局变量需要加锁；原子指令翻译和各类锁机制的实现
    • 调用pthread_create(pd, attribute, func, arg)，最后会调用glibc中的clone函数

    • TLS
      • TLS的数据是用__thread 或thread_local声明的。编译器会将 __thread 或 thread_local 变量放在 ELF 文件的 .tdata (initialized TLS data) 和 .tbss (uninitialized TLS BSS) 节中。这些节不直接映射到进程的主数据段，而是作为模板数据存在
      • 当一个新的线程通过 clone() 系统调用创建时（例如，由 pthread_create 调用），内核会为这个新线程分配一个独立的内存区域，称为 TLS 段。
      • 这个 TLS 段会根据 .tdata 节的内容进行初始化，.tbss 节则被零填充。
      • 每个线程都有一个特殊的寄存器（通常是 gs 或 fs 段寄存器，或一个专门的线程指针寄存器）指向其 TLS 段的起始位置。
        当代码访问一个 TLS 变量时，它会通过这个线程指针加上变量在 TLS 段中的偏移量来找到该变量的特定于线程的副本。

    260316（周一组会-寄存器分配）

    • 寄存器溢出：物理寄存器不够，把虚拟寄存器存到内存的方式

    • 在ENV中把所有标量寄存器和向量寄存器都存了一份（也就是内存中）

    • 为什么本地码中（翻译）用的是物理寄存器，而不是内存中映射的寄存器？——因为做了x86到rv寄存器的一对一（向量寄存器是一对二）映射，上下文切换会将ENV中所有的寄存器读到映射的寄存器中，以上进入本地码的时候，从本地码退出的时候，把物理寄存器的值写回到ENV中

    • rv上的向量寄存器数量不够多，所以xmm12-15没有进行映射，所以每次都只能从ENV中去读取使用

    • 优化的目的：减少load，store访存，找到固定映射和动态映射之间的平衡

    • Pass through 指令：这一类指令的目的寄存器只被部分修改，只要寄存器中的值没有被全部修改的指令都属于pass through指令

      • 比如Vslidedown vd, vs2, rs1, vm：语义是将vs2寄存器中的值右移rs1位赋给rd，rd的高rs1位保持原来的值不变

    • 变宽/变窄指令的特殊处理：比如TH_VWADDU_VX %0, $x0语义是将寄存器%0中的值与$x0相加，然后高位0扩展一倍的位数放到

    • 目前 RISC-V 机器也有32个向量寄存器，且位宽128位，我们需要合理的映射方案。

    • 翻译函数会产生一部分固定映射寄存器，还有一部分虚拟寄存器，主要是考虑x86的部分向量寄存器，两种方案：第一种是一一固定映射，第二种是动态映射，目前的方案是一部分固定映射，另一部分是动态映射

      • 一一映射，即全部固定映射。但是该方案不能覆盖所有使用的向量寄存器，指令翻译时会使用一些临时寄存器，这些临时寄存器会占用其他固定映射的寄存器。在TB 中，由于不知道当前指令点是否在这个 RISC-V 向量寄存器的活跃区间内，保守地认当前指令点在这个 RISC-V 向量寄存器的活跃区间中，因此溢出这个 RISCV向量寄存器就需要引入“store 保存旧值”和“1oad 恢复旧值”的开销。

      • 全部动态分配。对于编译器来说，使用的就是动态映射方案，这是由于不存在未知的代码片段，以及控制流也都是已知的。翻译函数决定了临时向量寄存器的活跃区间不会跨x86指令，进而不会跨 TB；但IR1 中的 xmm 和 ymm 是由x86 编译器在TU 级别分配的，它们的活跃区间可能跨TB。如果每个 TB 自由分配，会出现旧值被丢弃的问题。

        为了处理跨TB 的活跃区间，如果控制流识别完全，应该给跨TB 的活跃区间分配成同一个 RV 向量寄存器；但是二进制翻译中控制流识别不全，假设 TB1 的结尾有一个对xmm12的 DEF，这个 DEF 开启了一个活跃区间，但是这个活跃区间的结尾可能位于

    • 使用RAGreedy比原来的图着色的方案更好的原因是因为RAGreedy性能更好，因为它切分活跃区间的算法更好，寄存器溢出部分也处理更好（原来旧路线不论是动态还是静态是我们自己手搓的图着色分配算法，现在引入llvm，静态翻译修改成了RAGreedy）

    • MachineInstr：llvm定义的中间表示，LLVM有两层IR：LLVM IR（用于前端和中端）和MIR（用于后端）

      • 前端：高级语言层面
      • 中端：做机器无关的优化
      • 后端：面向具体机器架构的优化（RAGreedy是后端优化）

    • SSA静态单赋值原则，编译器中端寄存器无限多，后端才与具体的机器架构绑定

    • PHI 消除？

    • SBTRAGreedyReservePass：在正式分配之前，要对所有固定映射的物理寄存器进行保留设置，不参与寄存器分配

    • SBTFixDuplicateSuccessors：作用是将MBB重复的前驱后继都删除
