    BOLT搭建以及依赖

    一、源码下载以及构建编译

    • 关于使用BOLT优化的目标架构elf文件和编译BOLT的服务器架构： BOLT 基于 LLVM，LLVM 本身设计就是支持交叉编译和处理的。只要在编译 BOLT 时开启了 RISC-V 的 Target 支持（在cmake选项-DLLVM_TARGETS_TO_BUILD中加上优化的目标架构即可），x86 架构下编译得到的BOLT完全可以读取、分析和重写RISC-V 的ELF文件。

    • 工作流（以目标优化架构为RISC-V为例）：

      • x86架构的机器编译BOLT（不是绝对的，只要其他机器性能足够稳定。这里优先选择在x86上编译是因为主流x86架构的服务器性能更好，编译LLVM/BOLT非常消耗CPU和内存）
      • 在目标架构服务器上编译得到ELF文件，或者在x86服务器上使用<目标架构>-<目标操作系统>-gcc交叉编译，得到目标优化架构的ELF文件（在x86上编译rv是用riscv64-linux-gnu-gcc）
      • x86架构下可以直接使用bolt进行优化操作，或者使用perf（rv上）或者bolt- instrument（这个在x86上或者rv上都可以）事先使用插桩或者探针采样热点路径
        • 如果是instrument生成的bolt_test_rv64.inst文件，需要将其拷贝到rv机器上直接运行./bolt_test_rv64.inst > /dev/null，会生成bolt.fdata文件
        • 如果是perf生成的perf.data，需要用perf2bolt转换成perf.fdata文件（perf2bolt在x86上，如果rv机器编译了bolt，那么rv机器也可以）
      • 将.fdata文件和原ELF文件共同作为bolt输入：./bin/llvm-bolt bolt_test_rv64 -data=perf.fdata -o bolt_test_rv64.bolt -reorder-blocks=ext-tsp -reorder-functions=hfsort -split-functions -dyno-stats进行实际的bolt优化。

    • （如果是手动编译）源码下载：git clone https://github.com/llvm/llvm-project.git（llvm源码中包含BOLT）

    二、Cross Compiler 交叉编译器

    • 交叉编译器能产生不同架构指令，因为它其中包含了以下组件，所以能做到虽然==编译器本身运行在 x86 上==，但它拥有 RISC-V 的全部编译、汇编、链接环境，因此能生成 RISC-V 二进制文件。

    • 组件 用途
      前端（C/CPP parser） 跟普通 gcc 一样
      后端（target backend） 负责把 IR → 编码成 RISC-V 指令
      riscv64 binutils（ld / as / objdump） 链接成 RV64 ELF
      riscv64 glibc 链接运行时库、提供 RV64 版本的 libc.so

    三、编译选项

    • -Ox编译优化等级
      • -O0，不做任何优化
      • -O1，做基础优化（死代码消除，减少部分冗余循环）
      • -O2，平衡优化和编译时间（展开部分循环loop unroll；部分向量化）
      • -O3，激进优化（尽可能循环展开，尽可能向量化）
      • -Ofast，甚至违反标准的优化（浮点精度不保证）
    • -g生成调试信息，具体如下：
      • 会在ELF文件中生成.debug_* sections（开启此选项有利于BOLT更方便识别函数边界和符号，perf和bolt- instrument也依赖此调试信息）
    • -fno-omit-frame-pointer保留帧指针（默认情况下，优化器会取消 frame pointer（fp）以减少开销，perf和栈回溯分析都依赖RICS-V的s0和fp作为返回链条（call chain），如果取消帧指针，call graph信息会缺失，==BOLT官方明确要求编译时保留此选项==）
    • -Wl,--emit-relocs保留重定位信息，链接器选项（一些BOLT中的pass需要该信息，加上该选项可以使用更多BOLT中的pass，可以安全地对跳转进行重写，分析GOT/PLT调用，处理一些更复杂的RISC-V寻址模式，不加可能BOLT优化就只停留在改变代码布局上）

    五、问题记录

    按发生顺序

    1. 在 x86 上交叉编译出 RISC-V 的 bolt_test_rv64（成功）
    2. 在 x86 上用 BOLT 做 -instrument → 报错：arch x86_64 vs riscv64 冲突
    3. 尝试在 x86 上 单独给 BOLT 编 RISC-V runtime（bolt/runtime 下 make / cmake） → 各种 CMake / Makefile 错误
    4. 又尝试在同一个 build 目录里切换 CMake 源目录（runtime → llvm） → CMake cache 源不匹配错误
    5. 转而在 RISC-V 机器上重新 CMake + build LLVM+BOLT（host=RISCV）（成功）
    6. 在 RV 上对动态链接的 bolt_test_rv64 做 -instrument → 报错：Offset overflow for dynamic relocation
    7. 在 RV 上用 perf record + perf2bolt（无 -ba，尝试 brstack 模式）→ profile 为空（0 brstack entries）
    8. 在 RV 上改用 perf2bolt -ba + llvm-bolt 优化动态 ELF → 仍然在写回 ELF 时 Offset overflow for dynamic relocation
    9. 调整思路：改编译 静态 + 非 PIE 的 bolt_test_rv64_static（成功）
    10. 在 RV 上对 bolt_test_rv64_static 进行 perf record + perf2bolt -ba（成功得到非空 fdata）
    11. 第一次 llvm-bolt -data=perf_static.fdata → 文件名写错，报 No such file or directory
    12. 改为 -data=perf.fdata 再跑 llvm-bolt → 完全成功生成 bolt_test_rv64_static.bolt，无 relocation 错误，BOLT 完整优化一遍

    详细问题汇总表（含命令、现象、原因、后续方案）

    注：表格按时间顺序排列，每一行是一个“问题点”或紧接着的问题转折点。

    阶段 所在机器 / 环境 操作 / 指令（关键部分） 问题现象 / 报错信息 原因分析（技术结论） 后续方案 / 下一步
    1 x86 主机 ./bin/llvm-bolt bolt_test_rv64 -instrument -o bolt_test_rv64.inst 日志末尾：BOLT-ERROR: linking object with arch x86_64 into context with arch riscv64 BOLT 本身和其 runtime .o 是用 x86_64 构建的；现在试图对 RISC-V ELF 做 instrumentation 时，把 x86 runtime 对象 链接进一个 RISC-V 的链接上下文 → 架构不匹配，BOLT 检测到目标 arch 是 riscv64，但 runtime 是 x86_64，直接报错。 尝试“给 BOLT 单独编一套 RISC-V 版 runtime”，让 instrumentation 用 riscv64 的 runtime。
    2 x86 主机 在 llvm-project-main/bolt/runtime 下：make clean / make ARCH=riscv64 ... make: *** No rule to make target 'clean'. / No targets specified and no makefile found. 新版 BOLT runtime 使用的是 CMake 构建，该目录里没有传统 Makefile；直接 make 肯定报错。 改用 CMake 新建一个 bolt_runtime_rv64_build 目录来构建 runtime。
    3 x86 主机 在 bolt_runtime_rv64_build：
    cmake ../llvm-project-main/bolt/runtime -DCMAKE_C_COMPILER=riscv64-linux-gnu-gcc ... 然后 make -j    		 编译到链接 static lib 阶段时报：
    CMake Error: cmake version 3.28.3 Usage: /usr/bin/cmake -E <command> ...，lib/libbolt_rt_hugify.a / libbolt_rt_instr.a 生成失败    		 这个独立 CMake 工程默认生成 静态库，而 BOLT 实际需要的是编译过程中产生的 .o；同时该 CMake 使用 cmake -E 做一些安装 / 打包动作，当前构建配置有问题导致 cmake -E 被错误调用。总之这条路构建出来的东西和 BOLT 期望的 runtime 形态不一致，且当前配置下直接失败。 认识到单独构建 runtime 很绕，也容易踩 CMake 的坑；转而考虑：要么从 LLVM 顶层统一构建；要么干脆换到 RISC-V 上 native build BOLT。
    4 x86 主机 在 同一个 bolt_runtime_rv64_build 目录里又执行：
    cmake ../llvm-project-main/llvm ...    		 报错：
    CMake Error: The source ".../llvm/CMakeLists.txt" does not match the source ".../bolt/runtime/CMakeLists.txt" used to generate cache.    		 CMake 构建目录关联的是一个固定的源目录；你先在这个 build 目录里用 bolt/runtime/CMakeLists.txt 生成过缓存，再改成指向 llvm/CMakeLists.txt，CMake 认为“同一个 build 目录不能换源项目”，所以直接拒绝。 意识到这个 build 目录已经“绑定”在 runtime 工程上，不能拿来构 LLVM 顶层工程；若要构顶层，需要新建一个干净的 build 目录。此时你转而把注意力放到 RV 机器上。
    5 RISC-V 服务器 RV8-Dev-4 在 ~/llvm-project-main/build：
    cmake ../llvm-project-main/llvm -DLLVM_ENABLE_PROJECTS="bolt" -DLLVM_TARGETS_TO_BUILD="RISCV" ...，再 make -j bolt    		 CMake 输出：
    LLVM host triple: riscv64-unknown-linux-gnu，Targeting RISCV in llvm-bolt，Building BOLT runtime libraries for riscv64 等，整体配置成功，构建也通过。    		 这一步说明：你现在在 RISC-V 上 native 构建了 BOLT，BOLT 本身也是 riscv64 可执行文件，runtime 也按 riscv64 ABI 编译，这样就规避了之前 x86↔RISCV 的 arch mismatch 问题。 准备在 RV 机器上直接对 RISC-V ELF 运行 BOLT（包括 instrumentation / perf / 优化），放弃原本“在 x86 上优化 RISC-V ELF”的方案。
    6 RISC-V 上，动态链接的 bolt_test_rv64 ./bin/llvm-bolt ~/bolt/bolt_test_rv64 -instrument -o bolt_test_rv64.inst 日志：
    BOLT-WARNING: Failed to analyze 17 relocations，
    末尾：BOLT-ERROR: Offset overflow for dynamic relocation    		 现在 BOLT 和 runtime 架构一致了，但目标 ELF 是 动态链接 / PIE，内部含有不少 RISC-V 的动态重定位（.rela.dyn 等）。instrumentation 会：
    1）插入 runtime、hot text；
    2）扩展代码段并生成动态重定位；
    在处理某个 RISC-V relocation 时，需要记录的 offset 超出了该 relocation 格式（例如 32bit 偏移）的编码范围，BOLT 检测到 overflow → 直接报错。    		 结论：在当前这类 动态链接 RISC-V ELF 上，BOLT 的 relocation 支持还不完善，instrumentation 模式很容易炸。于是转向：先用 perf + perf2bolt 做采样型 FDO，看是否能绕开这个问题。
    7 RISC-V 上，动态 ELF perf record -e cycles:u ~/bolt/bolt_test_rv64
    然后：
    ./bin/perf2bolt ~/bolt/bolt_test_rv64 -p perf.data -o perf.fdata（无 -ba）    		 输出：
    PERF2BOLT: read 55 samples and 0 brstack entries，
    PERF2BOLT-WARNING: all recorded samples for this binary lack brstack. ... wrote 0 objects，
    0 out of 13 functions ... have non-empty execution profile    		 默认 perf2bolt 期望 perf.data 中含有 branch stack（brstack/LBR） 信息，用来恢复控制流路径。但 RISC-V 当前内核/perf 不支持类似 x86 LBR 的硬件分支历史记录，所以 perf record 里没有 brstack，perf2bolt 在“brstack 模式”下自然得不到任何可用 profile，导致 profile 为空。 使用 perf2bolt 的 非 brstack 模式：-ba（basic aggregation，仅用采样落在各指令/函数上的密度做粗粒度热度估计），继续尝试 FDO。
    8 RISC-V 上，动态 ELF ./bin/perf2bolt ~/bolt/bolt_test_rv64 -p perf.data -o perf.fdata -ba 生成 fdata，然后：
    ./bin/llvm-bolt ~/bolt/bolt_test_rv64 -data=perf.fdata -o bolt_test_rv64.bolt -reorder-blocks=ext-tsp -reorder-functions=hfsort -split-functions -dyno-stats    		 perf2bolt 部分成功：4 out of 13 functions ... have non-empty execution profile；但 llvm-bolt 阶段末尾再次：
    BOLT-ERROR: Offset overflow for dynamic relocation    		 即使不用 instrumentation、只做 基于 perf fdata 的重排和重写，BOLT 在改写这类动态 PIE ELF 时仍然需要维护 / 重建某些动态 reloc，依然踩到同一个 RISC-V relocation offset overflow 的坑。这说明：问题不在 profiling 模式，而在 BOLT 对动态 RISC-V ELF 的 relocation 处理本身不完整。 决策：暂时不再折腾动态链接的 ELF，换用一个 静态 + 非 PIE 的测试程序，让 ELF 尽量简单，从而避开当前 BOLT 在 RISC-V 上的 relocation bug；同时，这个更适合做“验证 BOLT 功能”的最小环境。
    9 RISC-V 上，重新编译静态 ELF 使用类似：
    riscv64-linux-gnu-gcc bolt_test_rv64.c -O2 -g -fno-omit-frame-pointer -fno-pie -no-pie -static -Wl,--emit-relocs -o bolt_test_rv64_static    		 编译成功，无报错。 通过 -static + -fno-pie -no-pie 生成 静态、非 PIE 的可执行文件；这类 ELF 的重定位和段布局结构简单很多，不依赖动态装载器 / PLT / GOT，从而极大降低 BOLT 在处理 reloc 时踩坑的概率。 准备对 bolt_test_rv64_static 重新走一遍 perf → perf2bolt → llvm-bolt 全流程，验证在这种简化 ELF 上 BOLT 能否完整工作。
    10 RISC-V 上，静态 ELF perf record -e cycles:u ~/bolt/bolt_test_rv64_static 正常完成：perf.data (108 samples)，无错误。 采样 event 仍然是 cycles:u；静态 ELF 下采到的样本数量更多一些，但仍然不包含 brstack（RISC-V 限制），不过这次我们已经计划用 -ba，所以问题不大。 继续用 perf2bolt -ba 汇总 profile。
    11 RISC-V 上，静态 ELF + perf2bolt -ba ./bin/perf2bolt ~/bolt/bolt_test_rv64_static -p perf.data -o perf.fdata -ba 输出：
    static input executable detected，
    BOLT-WARNING: Failed to analyze 34 relocations（warning），
    read 108 basic samples，out of range samples ... 76 (70.4%)，
    wrote 6 objects，3 out of 891 functions ... have non-empty execution profile    		 - BOLT 成功识别这是静态可执行，其 relocation 分析仍有部分 RISC-V reloc 不认识（34 个），但只是 warning。
    - 静态链接把 libc/启动代码都塞进 ELF，所以函数总数多（891），但实际被 perf 采样到的只有 3 个函数——基本就是你的测试代码主热点，合理。
    - out of range samples 多与某些 kernel/vdso 或 BOLT 看不到的区域有关，对核心流程无伤大雅。总之：profile 已经是非空、可用的。    		 准备用 perf.fdata 驱动 llvm-bolt 对 bolt_test_rv64_static 做优化。
    12 RISC-V 上，第一次 llvm-bolt 调用（文件名误写） ./bin/llvm-bolt ~/bolt/bolt_test_rv64_static -data=perf_static.fdata -o bolt_test_rv64_static.bolt ... 直接报错：'perf_static.fdata': No such file or directory. perf2bolt 实际输出的文件名是 perf.fdata，这里手滑写成了 perf_static.fdata，所以 BOLT 找不到 profile 文件。 修正命令，把 -data=perf_static.fdata 改成 -data=perf.fdata 再跑一遍。
    13 RISC-V 上，静态 ELF + 正确的 llvm-bolt 优化 ./bin/llvm-bolt ~/bolt/bolt_test_rv64_static -data=perf.fdata -o bolt_test_rv64_static.bolt -reorder-blocks=ext-tsp -reorder-functions=hfsort -split-functions -dyno-stats 输出关键信息：
    • static input executable detected
    • basic block reordering modified layout of 1 functions
    • UCE removed 9 blocks and 18 bytes of code
    • 给出优化前/后的 dynostats 对比（分支数、向前/向后分支、taken/non-taken 等）
    • 末尾：setting __hot_start to 0x400000, __hot_end to 0x4000b2，没有再出现任何 relocation 错误    		 这一条说明：在 静态 + 非 PIE 的 RISC-V ELF 上，BOLT 成功：
    1）读入 perf.fdata；
    2）重建 CFG；
    3）对至少一个有 profile 的函数做了 basic block 重排；
    4）删除了一些不可达 BB；
    5）重新布局 hot text 区域，并成功写回 ELF。
    关键：不再出现 Offset overflow for dynamic relocation，说明这种编译方式规避了 BOLT 在 RISC-V relocation 支持上的现有限制。    		 得到第一个真正“被 BOLT 优化过的 RISC-V 静态 ELF”：bolt_test_rv64_static.bolt。后续可以：
    • 对比优化前后运行结果 / 性能；
    • 用 objdump 对比函数 / BB 布局；
    • 把这一整条流程写进实验报告 / 毕业论文。
