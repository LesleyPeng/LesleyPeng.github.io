    Pin对ELF/二进制的抽象模型

    概述

    • IMG = 一个被加载的 ELF 文件
    • SEC = 这个 ELF 里的一个 section（Pin 视角）
    • RTN = Pin 认为的“函数 / routine”（RTN 并不是“从反汇编自动识别出来的函数”，而是 Pin 能确认的“例程”，它的来源高度依赖符号信息）

    IMG

    • 和 /proc/self/maps 里的“一个文件映射”是同一个层级的概念

    • ==注意：映射和加载的区别==

      • 映射的时机是在进程启动exec()时，OS内核会读取文件的头部信息（如 PE 或 ELF 格式），确定代码段、数据段的大小，然后在虚拟地址空间里建立好映射关系。OS在进程的虚拟内存中“划地皮”，告诉进程：“从地址 A 到地址 B 这块区域，对应的是硬盘上某个可执行文件的第 X 字节到第 Y 字节。”此时，物理内存（RAM）里可能一字节的数据都没有

      • 加载的时机是OS如果真正执行到某段代码时，发现这一段代码或者是访问某个变量，发现这段代码or这个变量在在对应的物理内存中RAM不存在，Page Fault 时，OS才会真正把那一页数据从磁盘换到内存RAM里，这就是所谓的“延迟加载”。

      • 虚拟的好处：可以共享部分内存，比如多个进程可以把各自的虚拟地址空间“映射”到物理内存中同一份可执行代码上；映射允许操作系统设置权限；允许程序的大小超过物理内存的限制。

    • IMG_AddInstrumentFunction(ImageLoad, 0);，当 loader 把 ELF 映射进进程时，Pin 触发，会调用我们自定义的ImageLoad()，

    SEC

    • 抽象了一些.text, .plt, .got, .data段等，Pin 的 SEC 是“逻辑 section”，不等价于 mmap 段

    RTN

    • 被称作是一个例程，通常对应一个函数入口，所以就是可以抽象成一个函数

    • RTN的信息既不是通过自动CFG分析识别也不是通过prologue，RTN主要来源是符号信息：符号表.symtab，动态符号表dynsym，DWARF（如果存在），以及 Pin 内部对 PLT/thunk 的识别

    • 某个 static inline、无符号的小函数 → 可能没有 RTN

    • “函数未 strip”是什么意思？

      在 ELF 世界里，“strip” 通常指 从可执行文件/共享库里移除符号信息（以及可能的调试信息），以减小体积、避免泄露内部信息。

      常见情况

      • 未 strip（not stripped）：
        • 文件里还保留比较完整的 .symtab（静态符号表）以及 .strtab
        • 能看到很多函数名、局部函数、静态函数等
        • readelf -S a.out 会看到 .symtab
        • file a.out 往往会显示 not stripped
      • strip 过（stripped）：
        • .symtab 常被移除（最典型）
        • 但很多动态库仍会保留 .dynsym（动态符号表）用于动态链接——这部分通常包含“导出函数”（比如 libc 导出的 API）
        • 你还能看到导出符号（比如 printf），但看不到很多内部局部函数名
        • file libc.so.6 经常显示 stripped（不少发行版的库是 stripped，但仍保留 .dynsym）

      为什么这和 Pin 的 RTN 有关？

      Pin 的 RTN 信息很大程度依赖它能从 image 获取到的符号/元数据：

      • 如果 .symtab/调试信息丰富 → Pin 能识别更多 routine
      • 如果只剩 .dynsym → 仍能识别导出函数（这对你“库函数开头”通常就够用了）
      • 如果符号几乎都没了 → Pin 能识别的 RTN 会变少，你的“函数入口 set”覆盖就会变差
